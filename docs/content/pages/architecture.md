Mizuki 是一个 C++23 静态站点生成器。核心工作是把站点配置、文档与主题转换为一组确定的发布文件；监听和 HTTP 预览是在这条构建路径上增加的开发能力。本文描述当前源码的结构，供阅读实现、添加功能和排查错误时使用。

## 系统边界

```text
TOML 配置 ──┐
Markdown ───┼──> 配置与构建计划 ──> 页面数据与主题渲染 ──> 临时输出 ──> 发布目录
主题与资源 ──┘         │                    │
                       └── 输出路径与链接 ──┘

文件监听 ──> 再次调用同一条构建路径 ──> 成功后更新 HTTP 预览与 SSE 版本
```

发布目录中的网页可以独立托管，不需要 C++ 运行服务、模板引擎服务或数据库。`serve` 是本地开发服务器，监听 `127.0.0.1`；正式部署使用 GitHub Pages 等静态托管。

### 构建目标与依赖方向

| CMake 目标 | 职责 | 主要依赖 |
| --- | --- | --- |
| `mizuki_core` | 配置、解析、输出规划、主题渲染、事务发布、站点与文稿创建 | md4c、toml++、Inja、nlohmann/json、spdlog |
| `mizuki_dev` | 文件监听、开发服务器、浏览器刷新 | `mizuki_core`、efsw、cpp-httplib、spdlog |
| `mizuki` | 命令行解析、命令分发、进程退出码 | `mizuki_dev`、spdlog |

核心库可以在没有 HTTP 和文件监听的情况下构建站点。第三方依赖在 `cmake/third_party_*.cmake` 中固定版本，项目警告与格式化策略只施加给自己的目标。

Inja 通过 `Theme` 的实现隐藏；JSON 则是配置扩展参数和模板上下文的公共值类型，因此属于核心库公开依赖。默认主题通过 CMake 嵌入程序，初始化站点时可直接生成可编辑文件。

## 源码地图

所有路径均相对仓库根目录。

| 位置 | 关注的问题 |
| --- | --- |
| `src/cli/commands.cpp` | 命令支持什么参数，如何调用核心或开发模块 |
| `src/config/` | 配置文件、CLI 覆盖、TOML 参数类型与合并 |
| `src/parse/` | front matter、Markdown、标题 ID 与章节数据 |
| `src/build/plan.cpp` | 哪些输入被发布，它们占用哪些输出位置 |
| `src/build/links.cpp` | 本地链接指向哪个实际产物 |
| `src/build/context.cpp` | 页面与集合如何转换为主题上下文 |
| `src/build/builder.cpp` | 一次完整构建的协调入口 |
| `src/build/output_transaction.cpp` | 临时目录、提交与失败回滚 |
| `src/render/` | Inja 模板环境、HTML 链接扫描、RSS/sitemap |
| `src/dev/` | 监听、预览、配置切换与 SSE |
| `src/scaffold/` | `init` / `new` 与只创建、不覆盖的文件操作 |
| `src/util/` | 文件、日期、UTF-8 路径、URL、HTML 公共操作 |
| `tests/` | C++ 核心测试与 Python 完整流程测试 |
| `themes/default/` | 博客默认主题，也是初始化时嵌入的唯一主题来源 |
| `docs/` | 由 Mizuki 构建的本文档站 |
| `examples/minimal-theme/` | 可直接使用的最小主题，展示模板接口 |

## 一次构建的生命周期

命令从 `src/main.cpp` 进入 CLI。加载配置后，`build_site()` 负责协调构建，成功返回 `BuildStats`；遇到错误时抛出带上下文的异常，由命令边界记录并转换为失败退出码。

### 1. 加载与校验配置

`ConfigRequest` 分开保存配置路径与命令行覆盖值，`load_config()` 将它们合成拥有自身数据的 `SiteConfig`。这样监听期间重新读取配置时，CLI 的优先级不会丢失。

配置文件中的相对路径以文件所在目录为基准，CLI 中的相对路径以当前工作目录为基准。未知根级配置键、错误类型与非法值在这里报告。主题自由参数在 `[extra]` 下转为保留类型的 JSON。

`BaseUrl` 分开保存源站地址和部署路径。例如 `https://example.com/blog/` 对应源站 `https://example.com` 与经过编码、以斜杠开始和结尾的 `/blog/`。文件系统路径与 URL 编解码分别处理，不混用同一套字符串规则。

### 2. 校验输出位置与规划文件

`validate_output_path()` 先拒绝会覆盖输入、配置或危险位置的输出目录。`plan_build()` 随后扫描内容和主题资源，解析文档并形成 `BuildPlan`：

- `pages` 保存源路径、相对路径、目标路径、文档与分类。
- `assets` 保存需要复制的内容资源和主题资源。
- `articles` 保存按日期降序、输出路径升序排列的文章摘要。
- `independent_pages` 保存按输出路径升序排列的独立页面摘要；与文章共用 `ContentSummary`，只保存元数据和文稿自己的 `extra`。
- `listings` 保存每张首页的输出地址与文章切片。
- `taxonomies` 保存标签与分类，条目保存名称、全站文章索引与分页计划；复用已排序文章，不复制完整文稿。
- `page_urls` 将源 Markdown 路径映射为实际发布路径。
- `outputs` 记录最终文件，用于导航校验等后续步骤。

`parse_document()` 按开头分隔符选择解析器：`+++` 使用 toml++ 解析 TOML，`---` 使用简单字面值解析器。两者共用标题、日期、标签与分类校验和正文切分规则；TOML 严格检查内置字段与未知根级键，`[extra]` 复用 `template_value()` 转换为拥有数据的 JSON 对象，保留嵌套类型。

`content/pages/` 下的 Markdown 是独立页面；其他 Markdown 是文章。草稿不进入发布计划。首页始终生成，分页、归档与发布信息按配置加入同一份计划。文章的 `tags` 与 `categories` 在解析时校验、去除首尾空白并去重；独立页面拒绝非空条目。仅已发布文章参与聚合，有条目时才规划对应总览与列表。首页和条目列表共用 `plan_listings()` 计算分页，名称保留为原始目录名，URL 编码留在生成链接时处理。

所有产物通过同一个输出注册表登记。`post.md` 与 `post.html` 都占用 `post.html` 时会报错，错误包含目标位置和两个来源。文件与目录冲突、内容资源与主题资源冲突、ASCII 大小写别名同样在写入前拒绝，结果不依赖扫描覆盖顺序。

### 3. 准备主题与扩展参数

每次构建创建一个 `Theme`，读取可选的 `theme.toml`，并按需缓存布局、父模板和组件。`merge_extra()` 递归合并主题默认参数与站点覆盖：对象递归合并，数组和标量整体替换。

模板只能从主题的 `layouts/` 内加载，加载时校验路径、符号链接边界、循环依赖与最大深度。Inja 的解析与渲染错误会补充模板或源文档上下文。

### 4. 渲染文档并解析链接

每篇文档的正文先由 MD4C 按站点 `MarkdownOptions` 转换为 HTML。`[markdown]` 控制数学、脚注和提示块语法，数学默认关闭以保留旧正文的美元符号含义。标题处理基于实际生成的 HTML，收集 h1–h6、保留已有 ID、为其他标题生成不冲突的 ID，并加入章节链接。

HTML 分析返回拥有 HTML、标题列表、正文能力与代码语言列表的 `RenderedMarkdown`。代码块、注释等内容中的伪标题不会成为目录项；中文、HTML 实体和重复标题按统一规则处理。

同一轮 HTML 分析还识别代码块、数学节点、脚注区和提示块，将结果作为 `page.features` 与 `page.code_languages` 传给主题。主题按需加载 highlight.js、KaTeX 与样式；框架不插入浏览器脚本。默认主题的本地库、字体与许可证随 `init` 写出，较大的内嵌资源拆为多个小字面量，避免触及编译器的字符串长度限制。

构建器随后改写 HTML 中的链接。Markdown 链接查询 `page_urls`，因此指向缺失页面、草稿或内容目录之外会失败。根级资源路径加入部署前缀；相对资源保持其相对语义。查询参数与片段保留。

`page_context()` 为所有入口构造拥有数据的 JSON 上下文。`site.posts` 与 `site.pages` 分别提供全站已发布文章和独立页面摘要；当前文档及其正文保存在 `page` 中。`site.tags` 与 `site.categories` 提供全站条目和文章数量。根级 `posts`、`archives`、`pagination`、`taxonomy`、`terms` 与 `term` 的初始值为空集合、默认页码或空字段，随后由相应列表入口填入当前切片、年份分组或条目数据。

`summary_value()` 与 `summary_data()` 统一转换两类全站摘要、首页和条目切片及归档文章，按当前输出位置计算文稿与标签／分类 URL，主题不必重新推导目录关系。摘要始终不带正文，`extra` 保留各文稿自己的类型和嵌套结构；它与 `page.extra` 都不与 `site.extra` 隐式合并。全站集合只提供已有页面的数据，不创建额外输出。

模板渲染时，普通字符串表达式自动进行 HTML 转义；已生成正文通过 `{{ html(page.content) }}` 显式写入。变量值中的模板标记不会再次参与解析。主题掌握 HTML 结构，构建器不为导航、列表和分页预先拼接固定标记。主题中的 `url()` 函数以站点根目录为起点，将自定义资源路径编码并加上部署前缀，使封面等资源可以在不同深度的页面复用。

### 5. 渲染集合与发布信息

首页分页与归档复用计划中的文章顺序。首页与标签／分类条目页的根级 `posts` 只获得当前切片，归档的 `archives` 按年份分组，RSS 使用全部已发布文章；全站 `site.posts` 在每种页面上均保持完整。空站点也保留首页。标签和分类总览使用 `taxonomy.html`，条目列表使用 `term.html`，两者共享全站上下文与分页转换；没有条目时不读取这两个布局。

只有配置完整 HTTP(S) 源站地址时才生成 RSS 与 sitemap。canonical、RSS 与 sitemap 复用发布 URL 规则：列表页使用目录地址，普通文档保留 `.html`；sitemap 包含标签与分类总览及所有条目分页，RSS 仍只包含文章。

发布信息不使用本机构建时间、文件修改时间或本机时区。XML 输出进行转义和字符有效性检查，失败会进入同一条构建失败路径。

### 6. 提交输出事务

页面和资源首先写入输出目录旁的临时目录，全部完成后由 `OutputTransaction::commit()` 发布：

```text
规划和渲染失败 ───────────────> 旧输出继续保留

全部产物完成 ──> 旧输出改名为备份 ──> 临时输出改名为正式输出 ──> 清理备份
                                         │
                                         └── 失败时尝试恢复备份
```

`OutputTransaction` 通过 RAII 管理临时文件生命周期。下一次成功构建整体替换输出，因此删除文章、重命名资源、改成草稿、移除标签／分类或减少分页后，不会留下旧产物。

这个机制保证普通构建失败时保留旧站点，但目录替换期间可能短暂无法访问路径；它不提供进程崩溃恢复，也不支持多个进程同时写入同一个输出目录。恢复失败会报告仍保留旧数据的备份位置。

## 开发预览与配置热重载

`watch` 和 `serve` 都通过 `WatchSession` 触发同一个全量构建入口。文件事件负责标记变化，监听循环合并变化后重建；启用 `[build].incremental` 后，这些入口共享 Markdown 和页面缓存。产物相同时，预览不会发送本次刷新事件。

`WatchSession` 分别维护两份状态：

| 状态 | 更新时间 | 用途 |
| --- | --- | --- |
| 正在监听的配置 | 有效的新输入目录准备好后、构建前 | 即使候选构建失败，继续捕获修复操作 |
| 已成功发布的配置 | 构建成功后 | 确定预览正在提供哪份输出 |

监听配置文件的父目录可以覆盖编辑器用临时文件替换配置的保存方式。切换内容或主题目录时先准备新的监听器，再替换旧监听器。

`LiveReload` 把输出目录、部署路径和版本号放在同一份带锁快照中。HTTP 请求从一次快照取值，避免把新部署路径和旧输出目录混用。只有成功发布才递增版本并通知 SSE 客户端；浏览器按新部署路径保留当前页面位置和章节锚点。

自动刷新脚本在预览 HTML 响应时注入，不会写入静态产物。GitHub Pages 托管的只是普通网页，不需要连接 Mizuki 的 SSE 服务。

## 站点和文稿创建

`init` 使用构建时从 `themes/default/` 生成的嵌入资源，输出一份可编辑主题；不依赖源码的绝对路径或可执行文件旁的资源目录。

`new` 复用配置路径和文档解析规则，先验证目标路径与元数据，再创建文件。本地日期只在创建文稿时使用，不进入站点构建或发布信息生成。

底层 `FileCreation` 使用排他创建，不截断已有文件。操作未提交而失败时，只回收本次创建的文件和空目录，不递归删除其他内容。

## 为改动选择位置

| 需要实现的功能 | 优先修改的边界 | 应关注的验证 |
| --- | --- | --- |
| 新的主题字段 | `build/context` 与主题文档 | 值类型、空值、不同页面类型、相对 URL |
| 新的主题参数 | 主题 `theme.toml` 和模板 | 默认值、站点覆盖、配置热重载 |
| 新的输出页面 | `build/plan` 与 `build/builder` | 冲突、链接、旧产物清理、事务回滚 |
| Markdown 或标题能力 | `parse` | 实际 HTML、代码和注释、已有 ID、实体与重复标题 |
| URL 或部署前缀行为 | `util/url` 与 `build/links` | 根路径、中文、空格、编码、查询参数与片段 |
| 监听或预览行为 | `dev` | 真正的进程、HTTP、SSE、失败恢复与配置切换 |
| 初始化体验 | `scaffold` 与默认主题 | 仓库外建站、不覆盖已有文件、内嵌资源一致性 |

优先让功能落在已有职责里。拥有明确资源生命周期的对象适合 RAII；单次转换适合直接返回结果的函数。避免为一次操作增加互相依赖的 `load` / `render` / `get` 隐藏状态。

## 测试与阅读路径

C++ 测试直接链接核心库，验证文档所有权、模板复用、错误上下文与输出事务。Python 测试只用标准库，通过真实程序验证最终生成文件，并启动真正的监听和预览进程。

```sh
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
ctest --test-dir build -R 'mizuki.(theme|docs)' --output-on-failure
```

建议先读 `build/builder.cpp` 理解协调流程，再读 `plan.cpp`、`context.cpp` 和 `render/theme.cpp`。修改预览时，按 `dev/watch.cpp` → `dev/server.cpp` → `dev/live_reload.cpp` → `dev/preview.cpp` 阅读。

格式约定、单组测试与贡献要求见[参与贡献](contributing.md)。主题对外契约集中在[主题开发](themes.md)，构建产物的托管方式见[部署指南](deployment.md)。
